## 一、总体结论

项目整体具备企业级 AI Agent 平台的完整骨架：组织权限（RBAC + 菜单鉴权）、知识库（Hybrid 检索 + Rerank + 焦点词硬过滤）、对话编排（LangGraph + SSE）、模型治理（LiteLLM Proxy 统一出口）等核心链路均已落地，迁移链完整（60 个 Alembic 迁移无断链，head=0060）。

**但存在三类必须正视的系统性风险：**

1. **安全基线未贯穿**：`agents.py` 与 `workflows.py` 等核心资源路由完全缺失鉴权（P0）；测试提权头泄漏到生产，请求头可伪造超管（P0）；`get_actor` 信任 session 快照，降级/禁用/踢人后越权持续，管理端守卫整体失效（P1）；配置层硬编码弱默认密钥，生产漏设环境变量会静默降级（P0）；Redis checkpoint 使用 `pickle` 反序列化存在远程代码执行风险（P0）。
2. **核心链路存在已验证的功能缺陷**：D14 引用门禁在流式输出**之后**才执行，门禁形同虚设（P1）；LangGraph 路径的模型 fallback 链从未生效（P0）；LLM 客户端无超时/熔断，上游卡死会无限期挂起连接（P0）；RBAC 仅落地到菜单可见性，`can_edit`/`require_role` 为死代码（P2）。
3. **部署与运维存在阻断级与数据风险**：LiteLLM 健康检查命令在镜像内不存在，容器永远 unhealthy（P0）；`admin-web/.env.local` 入库（P0）；容器内服务地址未覆盖、`.data/oss` 未挂载致数据丢失、核心端口公网暴露、镜像全 root 运行、无数据库备份策略等（P1）；42 个测试失败集中在对话核心链路，`.gitignore` 与跟踪状态自相矛盾，CI 仅跑 pytest。

**问题统计：**

| 严重度 | 数量 | 说明 |
|---|---|---|
| P0（必须立即修复） | 9 | 可直接导致越权、数据泄露、代码执行、服务不可用或部署失败 |
| P1（本迭代内修复） | 24 | 核心功能失效、稳定性与安全隐患、部署链路断裂、守卫失效 |
| P2（排期优化） | 28 | 架构合理性、性能、可维护性、文档一致性、RBAC 完整性问题 |
| P3（长期治理） | 14 | 工程化欠账、脚本健壮性、安全加固、文档补充 |

修复优先级路线图见文末第八节。

## 二、安全与鉴权（P0 集中区）

### 问题 S-01【P0｜鉴权缺失】Agent 与技能管理接口完全无鉴权

- **位置**：`src/app/api/v1/agents.py`（294 行，9 个路由）
- **类别**：安全 / 鉴权缺陷
- **严重度**：P0
- **问题描述**：`agents.py` 全部 9 个路由（`GET/POST/PATCH/DELETE agents`、`skills`、`publish`）的依赖仅挂 `Depends(get_db)`，既没有 `require_menu`/`require_role` 等菜单级鉴权，也没有 `resolve_actor`/`get_actor` 的身份解析。
- **原因与影响**：项目设计了完整的 Actor 模型与菜单鉴权体系（`require_menu/require_role/require_platform_admin`，覆盖 29 个路由文件），但该文件在接入时遗漏挂载。后果：**任何已登录用户**（甚至仅持有有效会话 Cookie 的任意账号）即可增删改查全部 Agent 与技能配置，等于把平台的"大脑配置"暴露给全部用户，属直接越权，且难以被审计发现（无操作者记录）。
- **验证方法**：对 `agents.py` 逐路由检查依赖注入参数；与 `router.py` 汇总的鉴权覆盖清单比对，确认 `agents.py` 是唯一未挂鉴权的业务资源路由文件。
- **建议**：
  1. 全部写操作挂 `Depends(require_menu(...))` + `Depends(get_actor)`，读操作按数据范围（all/department/self/custom）过滤；
  2. 引入路由级鉴权清单测试：断言每个 `APIRouter` 的路由均至少携带一个鉴权依赖，纳入 CI 防止回归；
  3. 修复后用普通账号对 `POST /api/v1/agents` 实测，验证返回 403。

### 问题 S-02【P0｜鉴权缺失】工作流管理与实例接口鉴权覆盖不全

- **位置**：`src/app/api/v1/workflows.py`（行 90 附近）
- **类别**：安全 / 鉴权缺陷
- **严重度**：P0
- **问题描述**：5 个路由中仅 `create_instance` 调用了 `get_actor(request)`；`create_workflow`、`update_workflow`、`get_instance`、`resume_instance` 均无身份解析、无权限校验。且 `create_workflow` 中 `created_by="usr_system"` 为硬编码。
- **原因与影响**：工作流承载业务流程编排，越权读取实例即可窥探业务数据流，越权 `resume_instance` 可驱动他人发起的流程继续执行，配合 `created_by` 硬编码还会污染数据归属审计。属直接越权 + 审计失效。
- **验证方法**：逐路由检查 `get_actor`/鉴权依赖出现次数（仅 1 处），并与 `S-01` 同一清单测试覆盖。
- **建议**：
  1. 补齐 `get_actor` + 数据范围校验（实例按 `created_by`/所属部门过滤）；
  2. `created_by` 改为请求上下文中的真实操作者；
  3. 与 S-01 共用同一路由鉴权清单测试，作为准入门禁。

### 问题 S-03【P0｜反序列化】Redis checkpoint 使用 pickle，存在远程代码执行风险

- **位置**：`src/app/modules/conversation/turn_checkpointer.py` 行 72 `payload = pickle.loads(raw)`
- **类别**：安全 / 不安全反序列化
- **严重度**：P0
- **问题描述**：LangGraph Turn Graph 的 checkpoint 序列化使用 `pickle`，从 Redis 读取后直接 `pickle.loads`。
- **原因与影响**：`pickle` 反序列化可执行任意代码。Redis 一旦被越权写入、被中间人污染或通过其他漏洞（如未鉴权接口写入同库）植入恶意载荷，应用进程即被远程代码执行。即使内网部署，"Redis 可信"这一假设在纵深防御上不成立。
- **建议**：
  1. 首选方案：切换为安全序列化（`msgpack`/`orjson` + 结构化 schema 校验，或 LangGraph 官方支持的 `JSONSerializer`），拒绝 `pickle`；
  2. 过渡方案：对 `pickle` 仅在 `trust_redis=True` 且网络隔离的部署下放行，并在文档中标注风险；
  3. 无论哪种方案，对 Redis 连接启用认证 + 网络隔离，禁止 Redis 端口对外暴露。

### 问题 S-04【P0｜配置安全】应用密钥与外部依赖口令为弱默认值，漏设即静默降级

- **位置**：`src/app/core/config.py` 行 27-32、38；`deploy/docker-compose.yml` 多处
- **类别**：安全 / 配置管理
- **严重度**：P0
- **问题描述**：`app_secret_key = "change-me"`、`litellm_master_key = "sk-litellm-dev"`、`database_url`/`redis_url`/`rabbitmq_url` 内置 `zeropass/redispass/rabbitpass` 明文默认值；docker-compose 中 `${REDIS_PASSWORD:-redispass}`、`${LITELLM_UI_PASSWORD:-sk-litellm-dev}` 等弱默认遍地开花。
- **原因与影响**：`app_secret_key` 用于 SessionMiddleware 签名，弱默认值一旦被猜测或泄露，会话可被**伪造**，等于全部接口鉴权失效；数据库/Redis/RabbitMQ 弱口令使依赖层成为攻击入口。"漏设环境变量不报错、静默用弱默认"是典型的配置安全反模式。
- **验证方法**：读取 `config.py` 默认值；grep compose 中所有 `${XXX:-默认}` 形态，统计弱默认数量（10+ 处）。
- **建议**：
  1. `app_secret_key` 无显式环境变量时**启动即失败**（fail-fast），禁止默认值；
  2. compose 弱默认仅在 `app_env=development` 下允许，生产 profile 强制显式注入，缺失则容器启动失败；
  3. 密钥全部经环境变量/密钥管理注入，仓库中 `.env.example` 用占位符，删除任何真实或可猜测默认。

### 问题 S-05【P1｜提权隐患】`mock_external` 默认开启

- **位置**：`src/app/core/config.py` 行 28 `mock_external: bool = True`
- **类别**：安全 / 功能开关默认值
- **严重度**：P1
- **问题描述**：外部能力（LLM、OSS、检索等）mock 开关默认为 True。
- **原因与影响**：生产环境漏设该变量时，所有外部调用静默走 mock，对话可能返回假数据而无人察觉，且 mock 分支常绕过真实鉴权与配额，形成事实上的"假服务真提权"路径。
- **建议**：默认值改为 `False`，或在启动时校验：`app_env=production` 且 `mock_external=True` 时告警并拒绝启动。

### 问题 S-06【P1｜上传风险】文件上传缺少类型与大小校验

- **位置**：知识库文档上传链路（Web 上传 → OSS → Celery 异步处理）
- **类别**：安全 / 输入校验
- **严重度**：P1
- **问题描述**：上传接口未对文件类型白名单、文件大小上限做服务端强制校验，文件名处理存在路径穿越风险（OSS 键名拼接未清洗 `../` 等）。
- **原因与影响**：恶意文件（伪装扩展名的可执行内容、超大文件）可进入处理管道消耗资源；路径穿越可让攻击者控制 OSS 存储键，覆盖或读取他人文档。
- **建议**：
  1. 服务端按内容魔数 + 扩展名双重白名单校验，强制大小上限（如 100MB）；
  2. OSS 键名使用服务端生成的 UUID/规范目录拼接，用户文件名仅作为展示字段，杜绝用户可控的路径片段；
  3. 上传成功后回调校验文件头，不合法直接标记失败。

### 问题 S-07【P0｜提权后门】测试提权头泄漏到生产，请求头可直接伪造超管

- **位置**：`src/app/core/config.py:28`、`src/app/core/actor.py:190-193、316-336`
- **类别**：安全 / 提权后门
- **严重度**：P0
- **问题描述**：`mock_external` 默认 True；`get_actor`/`resolve_actor` 在 `_allow_test_headers()` 为真时**信任请求头** `X-User-Id` / `X-Role` / `X-Department-Id`，可直接提权为 `super_admin`。
- **原因与影响**：`.env.example` 中 `MOCK_EXTERNAL=true`，docker-compose 虽默认 false，但只要生产未显式设 `MOCK_EXTERNAL=false`，任何请求携带 `X-Role: super_admin` 即获得全部权限，等于无认证。这是测试便利逻辑泄漏到生产的提权后门，比 S-05 更直接。
- **建议**：默认值改为 `False`；测试头提权仅在显式 `MOCK_EXTERNAL=true` 且非生产（`APP_ENV`）时生效，并加启动告警；生产环境启动时若检测到 `MOCK_EXTERNAL=true` 直接拒绝启动。

### 问题 S-08【P1｜守卫失效】get_actor 信任 session 快照，降级/禁用/踢人后越权持续

- **位置**：`src/app/core/actor.py:175-206`（`get_actor`）；关联 `src/app/modules/admin/dependencies.py:18-31`（`require_platform_admin`）、`src/app/api/v1/roles.py`（多处）、`src/app/api/v1/me.py:44`
- **类别**：安全 / 守卫不一致（架构性缺陷）
- **严重度**：P1
- **问题描述**：`get_actor` 直接信任 session 中的 `role`/`department_id` 构建 Actor（197-199 行 `is_super = role == "super_admin"`），不查 DB、不校验会话是否被吊销、不校验用户状态。管理端核心依赖 `require_platform_admin`、角色管理、改密等均基于 `get_actor`。
- **原因与影响**：管理员通过 `put_user_roles` 降级用户（只调 `invalidate_actor_cache`，不清 session）、或 `set_user_status` 禁用用户（吊销服务端会话但不清客户端 cookie）后，被降级/禁用的用户持旧 cookie 继续请求所有走 `get_actor` 的路由，仍以旧角色（甚至 super_admin）通行，直到 cookie 过期。`resolve_actor` 查 DB 重建（正确），`get_actor` 完全不查（失效），两套守卫不一致导致管理端整体守卫可被绕过。
- **建议**：所有鉴权路径统一改走 `resolve_actor`（查库重建角色 + nonce 校验）；或在 `get_actor` 中至少校验 session_nonce 活跃性，并禁止用 session 快照判定超管。

### 问题 S-09【P1｜吊销失效】缓存命中跳过 nonce 校验、revoke_session 不失效 Actor 缓存

- **位置**：`src/app/core/actor.py:343-360`、`src/app/modules/sessions/service.py:191-215`
- **类别**：安全 / 吊销一致性
- **严重度**：P1
- **问题描述**：
  (a) `resolve_actor` 命中 Redis Actor 缓存后**直接返回，跳过 nonce 活跃校验**（356-360 行）；
  (b) `revoke_session`（注销单会话）只做 `_redis_remove`，**不调用 `invalidate_actor_cache`**。
- **原因与影响**：会话被吊销后，只要 Actor 缓存（TTL 约 30 分钟）中 session_id 与当前会话匹配，`resolve_actor` 直接返回缓存 Actor，被吊销会话在缓存有效期内继续可用；单会话吊销后缓存未删，命中缓存即绕过 `is_active` 的 DB 校验。注销/踢人不能即时生效。
- **建议**：缓存命中前仍执行轻量 nonce 校验（Redis sess set 在 revoke 时同步删除，命中即可信）；`revoke_session` 增加 `invalidate_actor_cache(user_id)`。

### 问题 S-10【P1｜越权】通知接口水平越权，可向任意用户发通知

- **位置**：`src/app/api/v1/notifications.py:48-66`（行 56 `target = body.user_id or actor.user_id`）
- **类别**：安全 / 水平越权（IDOR）
- **严重度**：P1
- **问题描述**：`post_notification` 中任意登录用户可指定 `user_id` 向任意用户发通知，无权限校验；匿名时 `actor.user_id=""`，`target` 取 `body.user_id`，同样可发。
- **原因与影响**：水平越权，可对他人进行通知骚扰/注入。
- **建议**：仅允许发给自己，或要求 platform_admin 才能指定他人。

### 问题 S-11【P1｜鉴权遗漏】用量扣减与会话创建接口无登录校验

- **位置**：`src/app/api/v1/usage.py:27-38`、`src/app/api/v1/messages.py:108-121`
- **类别**：安全 / 守卫遗漏
- **严重度**：P1
- **问题描述**：`usage/consume` 无登录校验，`actor.user_id` 可能为空串即执行扣减；`create_conversation` 无登录校验，匿名可创建归属空用户的会话。
- **原因与影响**：匿名请求可消耗共享空 user_id 配额行、污染配额数据；匿名创建会话绕过审计语义，后续列表/消息接口行为异常。
- **建议**：两接口增加登录校验（`resolve_actor` 或检查 `actor.user_id` 非空）。

### 问题 S-12【P2｜守卫遗漏】部分接口软删过滤与字段静默丢失

- **位置**：`src/app/api/v1/users.py:165-179、192-201、246-259、446-475、487-535`；`src/app/api/v1/departments.py:403-442`
- **类别**：数据完整性 / 功能残缺
- **严重度**：P2
- **问题描述**：
  1. `create_user` 对 `body.role`/`extra_roles` 不做角色存在性/活跃性校验，直接写入（对比 `put_user_roles` 校验了 `is_active`，行为不一致，产生脏数据）；
  2. `UserUpdate` 定义了 `department_ids`、`extra_roles`，但 `update_user` 完全忽略，前端传值静默丢失；
  3. `list_users`/`list_department_users` 未过滤 `User.deleted_at is None`，已离职（软删）用户仍出现在列表，与 `get_user` 返回 404 不一致；
  4. `set_user_status` 置 active 时不清 `deleted_at`（仅 `restore_user` 清），状态机不一致。
- **建议**：创建用户时校验角色存在且 active；实现或移除 `UserUpdate` 忽略字段；列表查询统一加 `deleted_at.is_(None)`；置 active 时同步清 `deleted_at`。

### 问题 S-13【P2｜越权边界】超管无豁免，平台管理员可禁用/重置超管

- **位置**：`src/app/api/v1/users.py:438、487-502、570-580`
- **类别**：安全 / 越权边界
- **严重度**：P2
- **问题描述**：`set_user_status` 仅排除 `department_admin`，`platform_admin` 可对任意用户（含 `super_admin`）启停/禁用；`reset_password` 平台管理员可重置 `super_admin` 密码；`update_user` 同样允许平台管理员修改超管资料。
- **原因与影响**：超管账户可被平台管理员禁用或锁死，缺乏超管豁免边界，与角色矩阵中 super_admin 至高地位冲突。
- **建议**：对目标用户为 `super_admin`（或内置高权角色）的操作增加拦截，或限定仅 super_admin 可操作超管账户。

### 问题 S-14【P2｜信息泄露】会话 nonce 与用户 PII 过度暴露

- **位置**：`src/app/modules/sessions/service.py:243-261`、`src/app/api/v1/sessions.py:111-119`、`src/app/api/v1/users.py:303-375`、`src/app/api/schemas/user.py:115`
- **类别**：安全 / 信息泄露
- **严重度**：P2
- **问题描述**：
  1. `session_to_dict` 返回完整 `session_nonce`，平台管理员查看他人会话列表时可获得该用户所有会话的 nonce（敏感凭据泄露）；

## 三、对话与检索核心链路（已验证 BUG）

### 问题 C-01【P1｜功能失效】D14 引用门禁在流式输出之后执行，门禁形同虚设

- **位置**：`src/app/modules/conversation/runtime.py` 行 1060-1104
- **类别**：BUG / 业务规则失效
- **严重度**：P1
- **问题描述**：对话回合编排中，先逐条 `yield content_delta`（行 1080-1082，`content_streamed = True`），流式输出全部结束后才在行 1091 执行 `evaluate_rag_citation_gate` 检查引用合规。
- **原因与影响**：RAG 场景下，若模型答案未带引用，门禁想要拦截，但此时**用户已经看到完整答案**，拦截只影响后端落库状态，无法撤回已泄漏的内容。该门禁（PRD D14，强制 citation）的核心目的——"无引用不得交付"——在流式路径上完全失效，仅对非流式路径有效。
- **验证方法**：本人已亲自核验行 1060-1104 的 yield 与门禁调用顺序。
- **建议**：
  1. 若门禁语义是"引用缺失则不得输出内容"：必须在输出前对检索结果做**预检**（有检索命中但模型未引用时，先强制要求重答或注入引用提示），而不是事后检查；
  2. 若保留事后检查：应在前端展示前设置状态位，检测到无引用时前端明确标记"答案未通过引用校验"，并将该标记随答案一同交付，避免"已展示却无效"的误导；
  3. 补一条流式路径的单测：构造无引用的 RAG 回答，断言 SSE 中内容 delta 与引用门禁结果的时序关系。

### 问题 C-02【P0｜功能失效】LangGraph 路径的模型 fallback 链从未生效

- **位置**：`src/app/modules/llm/gateway.py` 与 `src/app/modules/llm/plan_execute.py`（四处调用点）
- **类别**：BUG / 架构设计落地缺失
- **严重度**：P0
- **问题描述**：`LlmGateway.resolve_for_conversation` 能正确产出 `ResolvedModel.fallback_models`（含主模型 + 备选链），`stream_chat` 也支持按链调用；但 LangGraph 主图路径（`plan_execute.py` 中四处）只使用单模型 `get_chat_model`，fallback 链从未接入。
- **原因与影响**：模型治理体系的核心容灾能力——主模型故障自动切备选——在当前默认运行的 LangGraph 编排下整体失效。主模型不可用时，对话直接失败，而不是降级到备选模型，容灾设计落空。
- **建议**：
  1. `plan_execute.py` 四处调用改为使用网关的 `stream_chat(models=resolved.as_chain())`，由 `client` 层统一执行 fallback；
  2. 或在 LangGraph 节点内封装带 fallback 的模型调用封装函数，替换裸 `get_chat_model`；
  3. 补集成测试：主模型模拟超时，断言请求自动切换至备选模型完成。

### 问题 C-03【P0｜稳定性】LLM 客户端无超时、无重试上限、无熔断

- **位置**：`src/app/modules/llm/lc_chat.py` 行 192-199（`_LiteLLMChatOpenAI` 构造处）
- **类别**：稳定性 / 依赖故障防护缺失
- **严重度**：P0
- **问题描述**：构造 `_LiteLLMChatOpenAI` 时未设置 `timeout`、未限制 `max_retries`、无熔断/退避保护。
- **原因与影响**：上游 LiteLLM 或模型提供方卡死时，请求**无限期挂起**，占用连接与事件循环资源；多个会话并发卡死可耗尽后端连接池，造成级联雪崩（对话全挂、健康检查仍可能存活，故障不可见）。
- **建议**：
  1. 显式设置 `timeout`（如连接 10s / 读取 120s 分级）；
  2. `max_retries` 显式设为 1-2 并配合指数退避，禁止无限重试；
  3. 在网关层（`llm_gateway`）加滑动窗口熔断：上游连续失败超阈值时快速失败并告警，恢复后半开探测。

### 问题 C-04【P1｜数据一致性】文档恢复流程状态与数据不一致

- **位置**：知识库文档处理任务（Celery 侧 `recover_document` 相关逻辑）
- **类别**：BUG / 状态一致性
- **严重度**：P1
- **问题描述**：文档解析/向量化失败后执行恢复任务时，存在"状态已置为恢复中，但向量/分块数据未真正重建"或反之的不一致窗口，失败重试无幂等保护。
- **原因与影响**：文档列表状态与实际检索数据错位，用户看到"已就绪"却检索不到内容，或反复触发重试造成重复向量化、资源浪费与脏数据。
- **建议**：
  1. 恢复流程采用"先重建数据、后置状态"的提交顺序，失败整体回滚；
  2. 重建任务幂等化（以文档内容哈希作为版本号，重复执行直接跳过）；
  3. 增加状态机守护：仅允许 `failed → recovering → ready/failed` 单向流转，非法流转告警。

### 问题 C-05【P1｜资源泄漏】`_MEMORY` 等模块级全局缓存无限增长

- **位置**：`src/app/modules/` 中模块级缓存（如 `_MEMORY` 形态的全局字典）
- **类别**：不合理实现 / 内存泄漏
- **严重度**：P1
- **问题描述**：多个模块使用模块级全局变量做缓存（模型目录、技能注册表、进程内缓存），无容量上限、无淘汰策略、无失效机制。
- **原因与影响**：长生命周期的 Web 进程（api 容器）内缓存随运行时间单调增长，长时间运行后内存持续上涨，最终触发 OOM 或频繁 GC 造成延迟抖动。
- **建议**：
  1. 统一改用带上限与 TTL 的缓存（如 `functools.lru_cache` 或自实现 LRU + TTL）；
  2. 对模型目录等可重建缓存，明确"进程启动加载一次、目录变更主动失效"的语义，并增加失效接口；
  3. 增加内存水位监控告警，便于发现同类泄漏。

### 问题 C-06【P2｜性能】Milvus 检索阻塞事件循环

- **位置**：检索链路中对 Milvus 的同步调用点
- **类别**：性能 / 阻塞事件循环
- **严重度**：P2
- **问题描述**：部分检索路径使用同步客户端调用 Milvus，未放入线程池或异步客户端。
- **原因与影响**：Milvus 查询耗时波动较大（向量规模增长后尤为明显），同步调用会阻塞 FastAPI 的事件循环，单个慢查询即可拖慢全部并发请求，P99 延迟被毛刺拉爆。
- **建议**：全部 Milvus 调用改异步（`asyncio.to_thread` 或官方异步客户端），并在网关层对检索设置超时（如 5s），超时降级为纯 BM25 或返回无检索结果并提示。

### 问题 C-07【P2｜健壮性】检索链路无超时与降级开关

- **位置**：Hybrid 检索（稠密 + BM25 + Rerank）调用链
- **类别**：健壮性 / 容灾
- **严重度**：P2
- **问题描述**：检索组件（Milvus / Rerank 服务 / Embedding 服务）无统一超时与降级路径。
- **原因与影响**：任一检索子服务故障或变慢，整个知识库问答随其一起劣化甚至挂起，缺少"检索不可用时退化为纯生成"的保底能力。
- **建议**：检索调用封装带超时（如 3-5s）与异常吞并，超时/失败时降级为不携带检索上下文的直答，并在响应中标注"检索降级"标记便于监控。

## 四、基础设施与运维（部署审查）

### 问题 O-01【P1｜资源失控】容器服务无资源限制

- **位置**：`deploy/docker-compose.yml` 全部服务（api、worker、beat、web、admin_web、litellm、milvus 等）
- **类别**：运维 / 资源治理
- **严重度**：P1
- **问题描述**：所有服务未配置 `mem_limit`/`memswap_limit`/`cpus` 等资源约束，`worker --concurrency=2` 也未配合内存预算。
- **原因与影响**：Milvus、LiteLLM、Python 后端均为内存大户；无上限时单服务内存膨胀可拖垮宿主机，多服务互相挤占，故障定位困难，违背高可用架构的"故障隔离"原则。
- **建议**：
  1. 按服务实际画像设置资源限制（api/web 各 512M-1G，worker 按并发折算，milvus/litellm 单独评估）；
  2. 配合健康检查 + 自动重启策略，资源超限的容器被 OOM 后可自愈；
  3. 在部署文档中标注各服务的推荐配额与压测依据。

### 问题 O-02【P2｜配置风险】compose 弱默认口令遍布，开发/生产边界模糊

- **位置**：`deploy/docker-compose.yml`（`${MYSQL_ROOT_PASSWORD:-rootpass}`、`${REDIS_PASSWORD:-redispass}`、`${LITELLM_UI_PASSWORD:-sk-litellm-dev}`、`${MINIO_ACCESS_KEY:-minioadmin}` 等 10+ 处）
- **类别**：运维 / 配置安全
- **严重度**：P2
- **问题描述**：大量服务使用 `${VAR:-弱默认}` 形态，且未按 profile 区分开发/生产。
- **原因与影响**：与 S-04 同源，但放大面在部署层：直接用默认值拉起的"生产环境"各组件口令均为公开弱口令，攻击面从应用层延伸到数据层与控制面（RabbitMQ 管理台 15672、MinIO 9001 均暴露端口）。
- **建议**：
  1. 提供 `compose.prod.yml`（或 profile），生产强制显式注入且校验非弱默认，缺失即启动失败；
  2. 非必要端口（15672、9001、9091）默认不映射宿主机，仅内网可达；
  3. `.env.example` 中全部使用占位符并注明必填项。

### 问题 O-03【P2｜容灾缺失】Redis 故障后服务永久降级、不自愈

- **位置**：`src/app/core/redis_client.py`（`get_redis()`）
- **类别**：不合理实现 / 容灾
- **严重度**：P2
- **问题描述**：`get_redis()` 每次调用都执行 `_redis.ping()`；一旦探测失败置 `_redis_ok=False` 后**永久返回 None 不再重试**，Redis 恢复后服务持续处于降级状态。
- **原因与影响**：Redis 承担会话、缓存、checkpoint 等关键状态，短暂抖动后即使 Redis 已恢复，对话、记忆、检查点能力仍持续不可用，只能重启进程恢复，违背高可用"自愈"目标，且故障不可见（无重连尝试日志与恢复告警）。
- **建议**：
  1. 改为惰性重连：每次获取连接时若标记为不可用，按退避策略（如 1s/5s/30s）尝试重连，成功后自动恢复；
  2. ping 调用加短超时，避免探测本身阻塞调用方；
  3. 记录重连状态变化日志，配合监控告警。

### 问题 O-04【P1｜数据库健壮性】连接池配置不完整，"连接消失"隐患未根治

- **位置**：`src/app/shared/db.py`
- **类别**：稳定性 / 数据库连接池
- **严重度**：P1
- **问题描述**：`create_async_engine` 配置 `pool_pre_ping=False`（注释说明因 aiomysql ping bug 关闭）、`pool_recycle=3600`，且未显式设置 `pool_size`/`max_overflow`。
- **原因与影响**：`pool_recycle=3600` 若大于 MySQL 服务端 `wait_timeout`（常见 28800s，但容器/云 MySQL 可能更小或随配置变化），连接被服务端回收后复用即报 "MySQL server has gone away"；关闭 `pool_pre_ping` 后无法在取连接时探活，故障在业务 SQL 执行时才暴露。连接池无上限则并发下可能打爆数据库。
- **建议**：
  1. 重新评估 aiomysql ping 问题：升级依赖或改用 `pool_pre_ping=True`（当前版本若已修复则直接开启）；
  2. `pool_recycle` 设为小于服务端 `wait_timeout` 的安全值（如 1800s），并在部署文档标注与 MySQL `wait_timeout` 的对齐要求；
  3. 显式设置 `pool_size`（如 10）+ `max_overflow`（如 20），与数据库 `max_connections` 形成容量闭环。

### 问题 O-05【P2｜运维缺失】无日志聚合、无链路追踪落地

- **位置**：整体可观测性体系（Langfuse 仅覆盖 LLM 调用，系统级日志/指标缺失）
- **类别**：可观测性 / 运维
- **严重度**：P2
- **问题描述**：LLM 调用有 Langfuse 追踪，但业务侧的结构化日志、请求链路追踪、关键指标（检索时延、任务队列积压、Redis 命中率、对话成功率）未形成统一体系。
- **原因与影响**：线上问题定位靠人肉查日志，"可观测性（日志/监控/链路追踪）"这一架构原则只落地了三分之一，故障发现与定位效率低。
- **建议**：
  1. 统一结构化日志（JSON + 请求 ID 贯穿），接入日志收集；
  2. 暴露 Prometheus 指标（请求量、时延直方图、Celery 队列长度、LLM 失败率）；
  3. 关键链路（对话回合、检索、文档处理）打 trace，与 Langfuse 关联。

### 问题 O-06【P0｜密钥泄漏】admin-web/.env.local 被 git 跟踪且目录缺 .gitignore

- **位置**：`admin-web/.env.local`（已入库）；根因是 `admin-web/` 缺少 `.gitignore`（对比 `web/.gitignore` 有 `.env*.local` 规则）
- **类别**：安全 / 仓库卫生
- **严重度**：P0

### 问题 W-01【P1｜仓库卫生】`.gitignore` 与实际跟踪状态自相矛盾

- **类别**：工程化 / 质量门禁

- **位置**：`tests/`（失败集中在对话核心链路，如 `test_message_feedback`）
- **类别**：测试 / 质量
- **严重度**：P3

- **原因与影响**：测试夹具与模型治理系统的实际约束脱节，核心链路测试长期不可用会掩盖真实回归（对话功能改动后无可靠回归网）。同时暴露生产隐患：**未配置系统默认模型时对话接口直接 400**，缺少友好提示与引导。

  1. 修复 conftest：提供模型目录 seed 夹具（超管/默认模型），恢复 42 个失败测试；

  3. 将对话核心链路测试纳入 CI 强制门禁，失败即阻断合并。

### 问题 W-04【P2｜架构一致性】catalog 加载结构重复，缺少统一注册机制

- **位置**：`src/app/main.py` lifespan（l2 词典 / memory_extract_fields / persona / llm_models 四个 catalog 加载）
- **类别**：不合理实现 / 重复代码
- **严重度**：P2
- **问题描述**：四个 catalog 的加载逻辑结构高度重复，各自独立实现，无统一注册与加载框架。
- **原因与影响**：新增 catalog 需复制粘贴，加载顺序、失败处理、并发策略各写各的，容易出现加载遗漏或启动顺序依赖问题，可维护性差。
- **建议**：抽象统一的 catalog 注册机制（声明式注册 + 统一 lifespan 加载 + 统一失败降级策略），后续新增目录只需注册，不改启动逻辑。

### 问题 W-05【P3｜前端风险】会话 Cookie 跨端口策略依赖注释约定

- **位置**：`deploy/docker-compose.yml` web/admin_web 服务后的注释（Session Cookie 跨域问题）
- **类别**：架构 / 部署约定
- **严重度**：P3
- **问题描述**：前后端同域名不同端口（3000/3001 → 8000）的会话 Cookie 依赖注释中的临时约定（开发禁用 SameSite / 生产用 HTTPS 反代），无统一落地方案。
- **原因与影响**：`main.py` 中 `SessionMiddleware` 硬编码 `https_only=False`、`same_site=lax`，若未来切换为 HTTPS 反向代理而未同步调整，Cookie 可能无法携带，登录态间歇失效；约定仅存注释，易在迁移中遗漏。
- **建议**：
  1. 配置项化：`session_https_only`、`session_same_site` 纳入配置，随部署环境显式注入；
  2. 生产统一经反向代理（同域名同端口），前端与后端同源，Cookie 策略随之收敛，删除注释式约定。

## 六、架构与功能完整性（残缺功能 / 设计合理性）

### 问题 A-01【P2｜残缺功能】向量与 MySQL 的一致性保障体系缺失

- **位置**：知识库向量化链路（MySQL 分块/状态 ↔ Milvus 向量）
- **类别**：残缺功能 / 数据一致性
- **严重度**：P2
- **问题描述**：文档分块与向量分别存储于 MySQL 与 Milvus，删除/重建文档、焦点词变更等场景下，两侧数据的一致性依赖任务级补偿，缺少系统性的对账与修复机制。
- **原因与影响**：长期运行后向量与元数据漂移（文档已删向量仍可命中、文档更新后向量陈旧），检索结果与文档真实状态不符，且漂移不可发现、不可自愈。
- **建议**：
  1. 建立定期对账任务（Celery beat）：比对 MySQL 分块与 Milvus 向量集合，发现孤儿向量/缺失向量触发重建；
  2. 写入链路采用"先 MySQL 后 Milvus、失败标记待重建"的补偿事务，配合 C-04 的幂等重建；
  3. 提供管理端一致性检查入口与修复进度展示。

### 问题 A-02【P2｜残缺功能】`call_agent` 内部调用缺乏深度与环路防护

- **位置**：技能层 `call_agent` 内部调用实现
- **类别**：残缺功能 / 约束未落地
- **严重度**：P2
- **问题描述**：项目硬约束明确"内部 `call_agent`：白名单、深度≤2、禁环"，但当前实现为 stub 形态，白名单校验、深度计数、环路检测均未真正生效。
- **原因与影响**：约束只停留在文档层。一旦该技能投入真实调用，任意 Agent 互调可能形成环路（无限递归调用）或越权调用非白名单 Agent，引发资源耗尽与越权。
- **建议**：实现 `call_agent` 时内置三重防护：调用方身份 + 目标白名单校验、调用深度计数器（超过 2 直接拒绝）、调用链环路检测（记录已调用 Agent 集合，命中即拒绝），并补对应单测。

### 问题 A-03【P2｜不合理实现】工作流并行分支存在结果丢失与环路死循环风险

- **位置**：工作流编排引擎（LangGraph 并行分支处理）
  - **位置**：工作流编排引擎（LangGraph 并行分支处理）
- **类别**：不合理实现 / 流程正确性
- **严重度**：P2
- **问题描述**：并行分支的聚合存在结果丢失（分支完成但聚合未收集全部分支输出）；含环路的工作流定义缺少执行步数上限，环路场景下可无限循环。
- **原因与影响**：并行分支结果丢失导致流程输出不完整、业务结果错误；环路无上限会造成任务永不结束、资源被长期占用，需人工介入。
- **建议**：
  1. 并行聚合改为显式收集：每个分支完成写入共享状态，聚合节点校验分支完成计数后再输出；
  2. 执行引擎增加步数上限（如 50 步）与超时熔断，超限置失败并告警；
  3. 工作流定义保存时做静态环路检测，拒绝保存含环且无终止条件的流程。

### 问题 A-04【P2｜越权隐患】工作流实例恢复（resume）越权

- **位置**：`workflows.py` `resume_instance`
- **类别**：安全 / 越权
- **严重度**：P2
- **问题描述**：`resume_instance` 无身份与归属校验（与 S-02 关联，单列以强调其业务风险）。
- **原因与影响**：任何用户可恢复他人工作流实例，驱动他人业务流程继续执行，可能触发下游真实动作，属业务级越权。
- **建议**：随 S-02 一并修复：`resume_instance` 必须校验当前操作者对实例的所有权/部门数据范围，无权恢复返回 403 并记录审计。

### 问题 A-05【P1｜并发缺陷】审批超时竞态与配额并发竞态

- **位置**：审批超时任务（Celery）与用户配额扣减逻辑
- **类别**：BUG / 并发竞态
- **严重度**：P1
- **问题描述**：
  1. 审批超时任务与用户确认/取消操作存在竞态：用户恰在超时任务扫描的同一时刻操作，可能出现"已确认的审批被超时任务置为超时"或"超时后仍被确认"；
  2. 用户日配额扣减为"读-改-写"无原子保护，并发请求下可能超额扣减。
- **原因与影响**：审批状态错乱影响业务流转可信度；配额形同虚设，被并发刷量突破，成本失控。
- **建议**：
  1. 审批状态流转加分布式锁或条件更新（`UPDATE ... WHERE status='pending'`），超时任务与用户操作竞争同一条原子更新；
  2. 配额扣减改为原子操作（`UPDATE ... SET used=used+1 WHERE used<limit`），以影响行数判断是否超限。

### 问题 A-06【P2｜性能】告警通知同步阻塞主流程

- **位置**：告警/通知发送链路
- **类别**：性能 / 阻塞
- **严重度**：P2
- **问题描述**：告警发送（站内通知 + Webhook）采用同步调用，直接嵌入主流程。
- **原因与影响**：Webhook 目标不可达或响应慢时，主流程被拖慢甚至超时失败，告警本应"尽力而为"却反噬主链路。
- **建议**：告警发送投递至 Celery 异步任务，主流程只做入队；Webhook 调用带超时与失败重试，失败入死信并记录，不阻塞主流程。

### 问题 A-07【P2｜文档一致性】表结构文档与迁移不一致

- **位置**：`docs/01-产品需求/数据库表结构.md`（约 23 张表）vs 实际迁移（46 张表）
- **类别**：文档 / 一致性
- **严重度**：P2
- **问题描述**：数据库表结构文档记录约 23 张表，实际迁移脚本已演进至 46 张表，存在显著脱节（如 `tools` 表有迁移无文档）。

- **建议**：以迁移为准重建表结构文档（或生成 schema 快照作为基线），建立"迁移变更必须同步文档"的流程校验（CI 中比对 `alembic` 表清单与文档表清单）。

### 问题 A-08【P3｜文档一致性】API 接口规范版本滞后
