## 一、选型总览

| 层级 | 选型 | 备注 |
|---|---|---|
| **后端框架** | FastAPI（Python） | AI 生态原生、异步高性能 |
| **Agent 编排** | **LangGraph + LangChain** | Plan-Execute + ReAct；两层 FC |
| **LLM 网关** | **LiteLLM Proxy（开发 Compose 本地）** | 上游模型用**线上** API |
| **检索/数据层** | **LlamaIndex**（Agent 不可见） | 解析编排 + 检索 |
| **前端** | **Next.js 同仓双应用：`web/` + `admin-web/`** | 员工端系统对话/业务控制台 + 独立管理后台；工作流编辑器使用 React Flow；**同仓 monorepo（D34–D35）** |
| **对话入口** | **Web 系统对话**（本阶段） | OpenIM / 企业 IM **延后** |
| **LLM** | Agnes / MiniMax / OpenAI / 通义等 | 经 LiteLLM，开发可用线上 |
| **关系库** | MySQL 8.0+ | 业务事务 |
| **向量库** | Milvus | 稠密 + 稀疏 Hybrid |
| **图数据库** | Neo4j 社区版 | 单机，小规模 KG |
| **缓存** | Redis | 缓存 / 限流 / 会话 / LangGraph 状态 |
| **队列** | RabbitMQ + Celery | 异步；人工节点挂起 |
| **对象存储** | **线上 OSS**；MinIO 仅无外网时可选 | Web 上传写入 |
| **全文检索** | 默认不用独立 ES | BM25 由 Milvus Hybrid |
| **任务调度** | Celery Beat | 定时任务 |
| **监控** | Langfuse（自托管）+ Prometheus + Grafana | LLM + 系统 |
| **告警** | 站内通知 + Webhook（可选邮件） | 非 OpenIM |
| **部署** | K8s / Docker Compose | 生产 / 本地 |
| **文档解析** | MinerU + Unstructured；LlamaParse 可选 | 本地优先 |
| **Embedding / Rerank** | BGE-M3 / BGE-Reranker | 本地，建议独立扩缩 |
| **MCP** | 观望 | 暂不实现 |

## 二、选型理由详解

### 2.1 后端框架：FastAPI

| 维度 | 说明 |
|---|---|
| **生态匹配** | AI/LLM 生态 80% 是 Python（LangChain、LlamaIndex、Transformers），无缝集成 |
| **性能** | 基于 Starlette + Uvicorn，异步 IO，并发能力接近 Go |
| **开发效率** | Pydantic 数据校验、自动 OpenAPI 文档、类型提示 |
| **AI 库丰富** | LangChain、LlamaIndex、Sentence-Transformers、Milvus SDK 都是 Python 原生 |

**备选不选理由**：
- Spring Boot（Java）：AI 集成需桥接；启动慢、迭代慢
- NestJS（Node）：AI 库都是 Python 绑定，需跑子进程
- Go：性能强但 AI 库生态薄弱

---

### 2.2 前端：Next.js 同仓双应用（`web/` + `admin-web/`）

| 维度 | 说明 |
|---|---|
| **位置** | 员工端 `web/`、管理端 `admin-web/`，均与 `src/app` 同仓（D34–D35） |
| **Next.js** | 两个应用均使用 App Router；员工端承载系统对话与业务页，管理端独立构建发布 |
| **React Flow** | 员工端/业务控制台的工作流 DAG 编辑器 |
| **管理端组件** | Ant Design 5 + 主题令牌，支持明亮/暗黑/跟随系统三态 |
| **联调** | 两个前端分别将 `/api/*` rewrite 到 FastAPI `:8000`，使用同源 HttpOnly Session Cookie |
| **不选独立仓** | 现阶段单团队 / AI 开发，保持单仓契约；两个应用可独立部署与回滚 |

---

### 2.3 LLM：多模型混部

**为什么必须多模型**：

| 场景 | 适用模型 | 理由 |
|---|---|---|
| 简单分类、意图识别 | GPT-4o-mini / Qwen-Turbo | 便宜、快 |
| 复杂推理、代码生成 | Claude Sonnet / GPT-4o | 能力强 |
| 长文档分析 | Claude（200K） / MiniMax（1M） | 上下文长 |
| 中文场景 | 通义千问 / 文心一言 | 中文理解深 |
| 私有化部署 | Qwen2.5 / DeepSeek 本地 vLLM | 数据不出域 |

**关键：模型路由层**
```
请求进来 → 任务分类 → 选模型 → 调对应 provider
   ↓
fallback chain：主模型失败 → 备用模型（跨 provider）
```

**备选不单一选理由**：锁单一 provider → 单点故障 + 价格绑架

---

### 2.4 关系库：MySQL 8.0+

**选型理由**：
- 业务事务首选
- 生态成熟、运维工具丰富
- 8.0+ 支持 JSON 函数索引、窗口函数、CTE

**重要配置**：必须用 8.0+，老版本不支持 JSON 函数索引、窗口函数

---

### 2.5 向量库：Milvus

| 维度 | 说明 |
|---|---|
| **性能** | 分布式架构，十亿级向量毫秒级检索 |
| **国产开源** | LF AI 顶级，中文社区活跃 |
| **混合检索** | 原生支持稠密向量 + 稀疏向量（BM25）+ 元数据过滤 |
| **多索引** | HNSW、IVF、PQ、DiskANN 按场景选 |

**备选对比**：

| 备选 | 优点 | 缺点 | 不选理由 |
|---|---|---|---|
| Qdrant | Rust 写、性能强 | 分布式版成熟度不如 Milvus | 单机强，集群版不稳 |
| Weaviate | 内置模块化 | 重、运维复杂 | 杀鸡用牛刀 |
| PGVector | 和 PG 一起用 | 性能差（百万级吃力） | 数据量大后扛不住 |
| Chroma | 上手快 | 单机、不支持生产级 | 仅适合原型 |

---

### 2.6 图数据库：Neo4j 社区版（v0.2 调整）

**调整背景**：原方案选 NebulaGraph，但运维成本太高（需 3 节点集群 + etcd），不适合 200-2000 用户规模。

| 维度 | 说明 |
|---|---|
| **单机部署** | 一个包安装完即用，运维简单 |
| **Web UI 内置** | Neo4j Browser 直接看图谱、调试查询 |
| **Cypher 生态** | 教程、Stack Overflow 案例多 |
| **数据规模** | 单机千万级实体，远超 zeroAgent 需求 |

**未来扩展路径**：如需千亿级图谱，可平滑迁移到 NebulaGraph 集群。

---

### 2.7 缓存：Redis

**选型理由**：缓存首选没有争议
- 会话缓存
- 限流计数器
- 热点问答缓存
- 向量检索缓存

---

### 2.8 队列：RabbitMQ + Celery（v0.2 移除 Temporal）

**为什么移除 Temporal**：
- 不做超长跨天流程（> 24h）
- Temporal 是重量级组件（独立 server + 数据库 + worker）
- 部署、运维、学习成本高
- 当前需求用 Celery + RabbitMQ 完全够用

**职责分工**：

| 组件 | 用途 |
|---|---|
| **RabbitMQ** | 消息中间件（任务传输） |
| **Celery** | Python 任务调度框架 |
| **Celery Beat** | 定时任务调度 |

**Celery 用途**：
- 文档解析 / Embedding 生成
- Milvus 向量入库
- 命中测试
- 业务工作流 DAG 节点执行（配合实例快照）
- 异步记忆抽取

**人工确认节点（v0.3 强制约束）**：

```
节点需人工确认
   ↓
写入实例状态 waiting + 审批任务（IM/Web）
   ↓
**释放 Celery worker**（禁止阻塞等待）
   ↓
用户确认/拒绝/超时 → API 回调
   ↓
再投递「续跑」任务，从快照恢复执行
```

> 超时默认 30 分钟（与 PRD 高风险确认一致，工作流人工节点可单独配置）。

**为什么不直接调 API**：Celery 提供异步、重试、任务链、结果查询等能力，避免每个任务单独写一套。

---

### 2.9 对象存储：线上 OSS 为主（v0.3.2）

| 环境 | 选型 | 说明 |
|---|---|---|
| **开发** | **线上阿里云 OSS（推荐）** | 与 LLM 一样可走线上；与生产路径一致，少环境差异 |
| **生产 / 预发** | 阿里云 OSS | 固定 |
| **可选兜底** | 本地 MinIO（S3 兼容） | 仅无外网 / 无 AK 时用；`STORAGE_BACKEND=minio` |

**配置**：`STORAGE_BACKEND=oss`（默认）或 `minio`；业务代码统一 S3 SDK。

**文件入库**：Web 上传写入线上 OSS Bucket；仅 MinIO 模式时再改指向本地桶。

---

### 2.10 全文 / 关键词检索：Milvus Hybrid 为主（v0.3 收敛）

| 方案 | 定位 | 说明 |
|---|---|---|
| **Milvus Hybrid（稠密 + 稀疏/BM25）** | **默认主路径** | 与向量检索同库并行，满足 PRD「向量 + BM25 + Rerank」 |
| MySQL FULLTEXT + ngram | **不作主检索** | 可用于运维/简单后台搜标题，不进 RAG 主链路 |
| Elasticsearch | **可选扩容** | 建议文档分块 > 约 1000 万后再评估引入 |

**三路检索落地（默认）**：

```
并行：Milvus 稠密检索 ∥ Milvus 稀疏(BM25)  → 合并候选
   ↓
Rerank（BGE，仅 Top-50）→ Top-5
   ↓（可选四路）
Neo4j KG（超时 2s 跳过）
```

---

### 2.11 任务调度：Celery Beat（v0.2 简化）

| 场景 | 方案 |
|---|---|
| **简单定时任务** | Celery Beat（每日数据同步、定时清理等） |
| **长流程工作流** | MVP 不支持（超时即失败） |
| **数据 pipeline** | Celery 异步任务链 |

**为什么不用 Airflow**：Airflow 偏 ETL 场景，zeroAgent 任务没那么复杂。

---

### 2.12 监控：Langfuse（自托管）+ Prometheus + Grafana

| 组件 | 用途 |
|---|---|
| **Langfuse（自托管）** | LLM 专属 tracing：prompt、token、延迟、成本、反馈 |
| **Prometheus** | 系统指标：CPU、内存、QPS、错误率 |
| **Grafana** | 看板：可视化 |

**为什么自托管 Langfuse**：
- 企业内网部署，符合数据合规要求
- 避免 Langfuse Cloud 免费额度限制
- 数据自主可控

**部署方式**：Docker Compose（PG + ClickHouse + Redis + Langfuse Server）

---

### 2.13 部署：Kubernetes / Docker Compose

| 场景 | 选型 |
|---|---|---|
| **生产（多实例、高可用）** | K8s |
| **MVP / 内部测试** | Docker Compose |

**为什么不选其他**：
- 裸机：扩缩容靠人
- Serverless：冷启动不适合 IM 长连接
- Docker Swarm：生态已死

---

### 2.14 文档解析：本地优先（v0.3 收敛）

| 工具 | 角色 | 适用 |
|---|---|---|
| **MinerU** | **PDF 默认主解析器（本地）** | 复杂版式、表格、OCR；内网可部署 |
| **Unstructured / LlamaIndex Readers** | Office / HTML / 通用 | Word/PPT/Excel/Markdown/网页 |
| **LlamaParse** | **可选外呼** | 默认关闭；需合规评估 + 配置开关后才可对指定租户/环境启用 |

**与 LlamaIndex 关系**：LlamaIndex 负责解析流水线编排与分块（SmartChunker）；底层 PDF 默认调 MinerU，而非默认 LlamaParse。

**合规**：Langfuse 自托管的前提下，解析默认不出域；开启 LlamaParse 视为例外，需审计与密钥托管。

---

### 2.15 Embedding：BGE-M3（本地，独立扩缩）

**部署**：默认可 CPU；**建议独立推理服务/Pod**，与 FastAPI API 进程分离。

**资源评估**：
- 模型大小 ~2.3GB
- CPU：适合中低并发与离线入库；高并发对话易拖垮 TTFT/检索 SLA
- 容量规划：按「入库吞吐」与「在线 query Embedding」分队列；预留 GPU

**选型理由**：
- 智源开源；稠密/稀疏/多向量能力利于 Hybrid
- 中文场景优于通用英文 Embedding API
- 本地部署无按次 Embedding 费用

### 2.16 Rerank：BGE-Reranker（本地，与 Embedding 同池）

**约束**：
- 只对合并后的 **Top-50** 重排（禁止 Top-200）
- 与 Embedding 同推理池或独立 Rerank 副本，便于水平扩展
- 热问 / 精确缓存命中时跳过检索与 Rerank

### 2.17 Agent 编排：LangGraph + LangChain（v0.3 补齐）

| 维度 | 决策 |
|---|---|
| 框架 | LangGraph + LangChain |
| 模式 | Plan-Execute 大循环 + ReAct 小循环 |
| Agent 可见工具 | 技能 / `rag_search` / 内部 `call_agent` |
| 状态 | Redis |
| 可观测 | LangGraph trace + Langfuse |

### 2.18 LLM 网关：LiteLLM Proxy（v0.3.1）

| 维度 | 决策 |
|---|---|
| 作用 | 统一多 Provider、Fallback、计费计量入口 |
| **开发** | **Compose 内起 LiteLLM Proxy（本机）**；上游模型用**线上** Provider（API Key） |
| **生产** | 同架构；Proxy 可独立扩缩 |
| 配置 | DB + Web 包装 LiteLLM Admin API（或启动时挂 config.yaml） |
| 不可用 | 直接报错（见 PRD）；前端有限重试 |

> 说明：开发阶段**不要求**本地跑大模型权重；只需本地 Proxy + 线上 LLM。禁止业务代码绕过 Proxy 直连各厂商（便于 fallback/计量一致）。

### 2.19 检索框架：LlamaIndex（v0.3 补齐）

| 维度 | 决策 |
|---|---|
| 范围 | 文档解析流水线 + 检索（含 Hybrid / Rerank 集成） |
| 边界 | **不做** Agent 编排；Agent 只见 `rag_search` |
| 向量 | Milvus VectorStore |
| KG | 自定义 Retriever → Neo4j |

### 2.20 对话入口：Web 系统对话（本阶段）

| 维度 | 决策 |
|---|---|
| 形态 | 控制台「系统对话」页 + `/conversations` `/messages` SSE |
| OpenIM | **不接入**（D27） |
| 企业 IM | 产品级通道延后；未来可插拔适配器 |
| 文件 | Web 上传 → OSS → Celery |
| 身份 | Session = `user_id`，无 IM 映射表 |

### 2.21 告警通道

| 维度 | 决策 |
|---|---|
| 默认 | 站内通知（`notifications`） |
| 可选 | 通用 Webhook（可接飞书/钉钉机器人）；可选邮件 |
| 不做 | OpenIM 系统号推送（本阶段） |

### 2.22 MCP 协议：观望

**决策**：不引入 MCP；HTTP 工具 + 内置工具覆盖主场景。v1.1+ 再评估。

## 三、检索架构（v0.3）

### 3.1 检索路数配置化

| 路数 | 包含 | 适用场景 | 预估延迟 |
|---|---|---|---|
| **三路（推荐）** | Milvus 稠密 + Milvus 稀疏(BM25) + Rerank | 多数 Agent | ~300ms |
| **四路（增强）** | 三路 + Neo4j KG | 复杂关系查询 Agent | ~500ms（KG 超时 2s 跳过） |

### 3.2 性能优化策略

| 优化点 | 方案 |
|---|---|
| **并行检索** | 稠密 ∥ 稀疏（+ 可选 KG）并行，最后 Rerank |
| **Rerank 限制** | 只对 Top-50 重排 |
| **缓存** | Redis 精确/语义缓存；命中则跳过检索 |
| **降级** | KG 超时跳过；推理过载时降级为仅稠密或跳过 Rerank（需告警） |
| **扩缩** | Embedding/Rerank 独立 Pod，与 API 分离 |
